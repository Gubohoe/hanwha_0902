# 2. 메모리

## 2.1 메모리란?

LLM은 기본적으로 이전 대화 내용을 자동으로 기억하지 않는다.

따라서 여러 번의 대화를 이어가기 위해서는 이전 대화 내용을 저장하고 다음 요청에 함께 전달하는 메모리가 필요하다.

```text
사용자 질문
    ↓
LLM
    ↓
답변
    ↓
대화 내용 저장
    ↓
다음 질문
    ↓
이전 대화 내용 + 새로운 질문
    ↓
LLM
```

메모리를 사용하면 여러 번의 요청에서도 이전 대화의 맥락을 유지할 수 있다.

# 3. 대화 버퍼 메모리

## 3.1 개념

대화 버퍼 메모리는 지금까지의 대화 내용을 그대로 저장하는 방식이다.

```text
Human: 안녕하세요.
AI: 안녕하세요. 무엇을 도와드릴까요?

Human: 저는 Python을 공부하고 있어요.
AI: Python 공부를 도와드릴게요.
```

새로운 질문이 들어오면 기존 대화 내용을 함께 활용할 수 있다.

```text
이전 대화 전체
       +
새로운 질문
       ↓
      LLM
       ↓
     답변
```

### 특징

- 이전 대화 내용을 그대로 보존한다.
- 대화가 길어질수록 저장하고 전달해야 하는 내용이 많아진다.
- 짧은 대화에서 사용하기 적합하다.

---

# 4. 대화 버퍼 윈도우 메모리

## 4.1 개념

대화 버퍼 윈도우 메모리는 전체 대화가 아니라 **최근 일정 개수의 대화만 유지**하는 방식이다.

예를 들어 최근 2개의 대화만 유지한다고 하면:

```text
대화 1  → 삭제
대화 2  → 삭제
대화 3  → 유지
대화 4  → 유지
```

즉, 오래된 대화는 제외하고 최근 대화만 LLM에 전달한다.

### 특징

- 대화가 길어져도 전달되는 내용의 양을 제한할 수 있다.
- 최근 대화의 맥락을 유지할 수 있다.
- 오래된 대화 내용은 기억하지 못할 수 있다.

---

# 5. 대화 토큰 버퍼 메모리

## 5.1 개념

대화 토큰 버퍼 메모리는 **토큰 수를 기준으로 대화 내용을 관리**한다.

LLM에는 한 번에 처리할 수 있는 토큰의 양이 제한되어 있기 때문에 토큰 기준으로 메모리를 관리할 수 있다.

```text
대화 내용
   ↓
토큰 수 계산
   ↓
설정된 토큰 한도 확인
   ↓
한도 초과 시 오래된 대화 제거
```

### 특징

- 대화 개수가 아니라 토큰 수를 기준으로 관리한다.
- LLM의 컨텍스트 길이를 고려할 수 있다.
- 긴 대화에서 토큰 사용량을 관리하는 데 유용하다.

---

# 6. 대화 엔티티 메모리

## 6.1 개념

대화 엔티티 메모리는 대화에서 등장하는 **중요한 엔티티 정보를 기억**하는 방식이다.

예를 들어:

```text
사용자:
제 이름은 홍길동이고 Python 개발자가 되고 싶어요.
```

메모리에 다음과 같은 정보가 저장될 수 있다.

```text
이름 → 홍길동
관심 분야 → Python
목표 → 개발자
```

이후 대화에서 사용자의 정보를 활용할 수 있다.

### 특징

- 대화 전체를 저장하는 것이 아니라 중요한 정보를 중심으로 관리한다.
- 사용자 이름, 관심사, 프로젝트 등 특정 정보를 기억하는 데 활용할 수 있다.

---

# 7. 대화 지식 그래프 메모리

## 7.1 개념

대화 지식 그래프 메모리는 대화에서 얻은 정보를 **관계가 있는 그래프 형태**로 표현하는 방식이다.

예:

```text
홍길동
  │
  ├── 관심 → Python
  │
  ├── 공부 → AI
  │
  └── 목표 → 개발자
```

정보를 단순한 문자열이 아니라 엔티티와 관계로 표현할 수 있다.

### 특징

- 엔티티 간의 관계를 표현할 수 있다.
- 복잡한 관계형 정보를 관리하는 데 활용할 수 있다.
- 대화에서 등장하는 정보의 관계를 추적할 수 있다.

---

# 8. 대화 요약 메모리

## 8.1 개념

대화 요약 메모리는 긴 대화 전체를 그대로 저장하지 않고 **대화 내용을 요약하여 저장**하는 방식이다.

예:

```text
긴 대화
   ↓
요약
   ↓
"사용자는 Python과 AI 개발을 공부하고 있으며
개발자 취업을 준비하고 있다."
```

이후 새로운 질문이 들어오면 요약된 내용을 활용한다.

### 특징

- 긴 대화를 짧게 관리할 수 있다.
- 전체 대화를 그대로 전달하는 것보다 토큰 사용량을 줄일 수 있다.
- 요약 과정에서 세부 정보가 사라질 수 있다.

---

# 9. 벡터 스토어 검색 메모리

## 9.1 개념

벡터 스토어 검색 메모리는 대화 내용을 벡터로 변환하여 저장하고, 새로운 질문과 관련성이 높은 과거 대화를 검색하여 사용하는 방식이다.

```text
대화 내용
    ↓
Embedding
    ↓
Vector
    ↓
Vector Store 저장
```

새로운 질문이 들어오면:

```text
새로운 질문
    ↓
Embedding
    ↓
유사한 과거 대화 검색
    ↓
관련 대화
    ↓
LLM
```

### 특징

- 전체 대화를 항상 전달하지 않아도 된다.
- 현재 질문과 관련된 과거 내용을 검색할 수 있다.
- 대규모 대화 기록을 관리할 때 활용할 수 있다.

# 11. LCEL 체인에 메모리 추가하기

## 11.1 LCEL이란?

LCEL(LangChain Expression Language)은 LangChain의 여러 컴포넌트를 연결하여 하나의 실행 흐름을 만드는 방식이다.

```text
Prompt
   ↓
LLM
   ↓
Output Parser
```

LCEL을 사용하면 각 컴포넌트를 체인 형태로 연결할 수 있다.

---

## 11.2 메모리를 포함한 체인

메모리를 사용하는 경우 이전 대화 내용을 프롬프트에 함께 전달해야 한다.

```text
사용자 입력
    ↓
메모리에서 이전 대화 가져오기
    ↓
Prompt에 대화 내용 추가
    ↓
LLM
    ↓
답변
    ↓
메모리에 대화 저장
```

즉, 메모리는 LCEL 체인의 입력과 출력 과정에 함께 연결하여 사용할 수 있다.

# 12. SQLite에 대화 내용 저장하기

## 12.1 SQLite란?

SQLite는 별도의 데이터베이스 서버 없이 사용할 수 있는 파일 기반 데이터베이스이다.

대화 내용을 SQLite에 저장하면 프로그램이 종료되어도 대화 기록을 유지할 수 있다.

```text
사용자 입력
    ↓
LLM
    ↓
답변
    ↓
SQLite
    ↓
대화 기록 저장
```

---

## 12.2 SQLite 저장 예시

```python
import sqlite3

conn = sqlite3.connect("conversation.db")

cursor = conn.cursor()

cursor.execute("""
CREATE TABLE IF NOT EXISTS conversations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    role TEXT,
    content TEXT
)
""")

cursor.execute(
    "INSERT INTO conversations (role, content) VALUES (?, ?)",
    ("user", "안녕하세요.")
)

conn.commit()
conn.close()
```

저장된 대화는 이후 다시 조회할 수 있다.

```python
conn = sqlite3.connect("conversation.db")
cursor = conn.cursor()

cursor.execute("SELECT role, content FROM conversations")

rows = cursor.fetchall()

for row in rows:
    print(row)

conn.close()
```

# 13. 휘발성 메모리로 일반 변수에 대화 내용 저장하기

## 13.1 개념

가장 간단한 방법은 Python의 일반 변수를 이용하여 대화 내용을 저장하는 것이다.

```python
conversation_history = []
```

사용자 메시지를 저장한다.

```python
conversation_history.append({
    "role": "user",
    "content": "안녕하세요."
})
```

LLM의 답변도 저장한다.

```python
conversation_history.append({
    "role": "assistant",
    "content": "안녕하세요. 무엇을 도와드릴까요?"
})
```

현재 대화 내용:

```python
print(conversation_history)
```

---

## 13.2 휘발성 메모리의 특징

일반 변수에 저장한 대화 내용은 프로그램의 메모리에 존재한다.

```text
Python 프로그램 실행
       ↓
conversation_history
       ↓
대화 내용 저장
```

하지만 프로그램이 종료되면 데이터가 사라진다.

```text
프로그램 종료
       ↓
메모리 데이터 삭제
```

따라서 이를 **휘발성 메모리**라고 할 수 있다.

### 장점

- 구현이 매우 간단하다.
- 별도의 데이터베이스가 필요하지 않다.
- 테스트용으로 사용하기 쉽다.

### 단점

- 프로그램 종료 시 데이터가 사라진다.
- 서버가 여러 개이면 메모리를 공유하기 어렵다.
- 장기적인 대화 기록 저장에는 적합하지 않다.

---

# 14. 휘발성 메모리와 SQLite 비교

| 구분 | 일반 변수 | SQLite |
|---|---|---|
| 저장 위치 | 프로그램 메모리 | 파일 |
| 프로그램 종료 | 데이터 삭제 | 데이터 유지 |
| 구현 난이도 | 낮음 | 상대적으로 높음 |
| 장기 저장 | 어려움 | 가능 |
| 테스트 | 적합 | 적합 |
| 영속성 | 없음 | 있음 |

# 15. Git Branch

## 15.1 Branch란?

Branch는 하나의 프로젝트에서 **독립적인 작업 공간을 만드는 기능**이다.

예:

```text
main
 │
 ├── feature/login
 ├── feature/chat
 └── feature/memory
```

각 기능을 별도의 Branch에서 개발할 수 있다.

---

## 15.2 Branch 생성

```bash
git branch feature/login
```

Branch를 생성하면서 이동할 수도 있다.

```bash
git switch -c feature/login
```

현재 Branch 확인:

```bash
git branch
```

---

## 16.3 Branch를 사용하는 이유

- 기능별로 작업을 분리할 수 있다.
- 기존 코드에 영향을 최소화할 수 있다.
- 여러 개발자가 동시에 작업할 수 있다.
- 실험적인 기능을 안전하게 개발할 수 있다.

---

# 16. Git Merge

## 16.1 Merge란?

Merge는 한 Branch에서 작업한 변경 내용을 다른 Branch에 합치는 것이다.

예:

```text
main
 │
 └── feature/login
          ↓
        작업 완료
          ↓
        merge
          ↓
main
```

명령어:

```bash
git switch main
git merge feature/login
```

---

## 16.2 Merge Conflict

서로 다른 Branch에서 같은 부분의 코드를 수정하면 충돌이 발생할 수 있다.

```text
Branch A
   ↓
같은 코드 수정
   ↘
     충돌
   ↗
같은 코드 수정
   ↓
Branch B
```

충돌이 발생하면 개발자가 충돌 부분을 직접 수정한 후 다시 Merge해야 한다.

---

# 17. Pull Request

## 17.1 Pull Request란?

Pull Request(PR)는 자신이 작업한 Branch의 변경 내용을 다른 Branch에 반영해 달라고 요청하는 협업 방식이다.

일반적인 흐름:

```text
Branch 생성
    ↓
코드 작성
    ↓
Commit
    ↓
Push
    ↓
Pull Request 생성
    ↓
Code Review
    ↓
Merge
```

Pull Request를 사용하면 다른 개발자가 코드를 검토한 후 Merge할 수 있다.

---

## 17.2 Pull Request를 사용하는 이유

- 코드 리뷰
- 변경 내용 확인
- 협업 과정 관리
- 버그나 문제점 발견
- Merge 전 코드 품질 확인

---

# 18. CI/CD

## 18.1 CI란?

CI(Continuous Integration)는 **지속적 통합**을 의미한다.

개발자가 코드를 변경하여 저장소에 반영하면 자동으로 빌드나 테스트 등을 수행하여 코드의 문제를 빠르게 확인할 수 있다.

```text
코드 변경
   ↓
Push
   ↓
CI 실행
   ↓
Build / Test
   ↓
결과 확인
```

---

## 18.2 CD란?

CD는 Continuous Delivery 또는 Continuous Deployment를 의미한다.

코드 변경 이후 배포 과정을 자동화하여 개발된 애플리케이션을 빠르게 배포할 수 있도록 한다.

```text
코드 변경
   ↓
Build
   ↓
Test
   ↓
Deploy
   ↓
서버에 반영
```

---

# 19. CI/CD 전체 흐름

Git을 사용하는 프로젝트에서는 다음과 같은 흐름으로 구성할 수 있다.

```text
개발자
  ↓
Branch
  ↓
코드 작성
  ↓
Commit
  ↓
Push
  ↓
Pull Request
  ↓
Code Review
  ↓
Merge
  ↓
CI
  ↓
Build / Test
  ↓
CD
  ↓
Deploy
```

CI/CD를 구축하면 코드가 변경될 때 테스트와 배포 과정을 자동화할 수 있다.

# ⭐ 오늘의 핵심

- LLM은 이전 대화를 자동으로 기억하지 않기 때문에 대화 내용을 관리하기 위한 메모리가 필요하다.
- 대화 버퍼 메모리는 전체 대화를 저장한다.
- 대화 버퍼 윈도우 메모리는 최근 대화만 유지한다.
- 대화 토큰 버퍼 메모리는 토큰 수를 기준으로 대화를 관리한다.
- 대화 엔티티 메모리는 중요한 엔티티 정보를 기억한다.
- 대화 지식 그래프 메모리는 엔티티와 관계를 그래프 형태로 관리한다.
- 대화 요약 메모리는 긴 대화를 요약하여 저장한다.
- 벡터 스토어 검색 메모리는 관련성이 높은 과거 대화를 검색하여 활용한다.
- LCEL 체인에서도 이전 대화 내용을 입력에 포함하여 메모리를 구성할 수 있다.
- 일반 변수에 대화 내용을 저장하면 프로그램 종료 시 데이터가 사라지는 휘발성 메모리가 된다.
- SQLite를 사용하면 프로그램이 종료되어도 대화 내용을 파일에 저장할 수 있다.
- Git Branch는 기능별로 독립적인 작업 공간을 만드는 기능이다.
- Merge는 서로 다른 Branch의 변경 내용을 합치는 작업이다.
- Pull Request는 변경 내용을 검토하고 Merge하기 위한 협업 과정이다.
- CI는 코드 변경 시 빌드와 테스트 등을 자동으로 수행하는 과정이다.
- CD는 검증된 코드를 배포하는 과정을 자동화하는 것이다.
- **메모리는 대화의 맥락을 관리하고, Git은 코드의 변경과 협업 과정을 관리한다.**
